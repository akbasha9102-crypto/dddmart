# تصميم: ترقية أول حساب لـ "صاحب محل" تلقائياً + إخفاء بيانات الربح عن الكاشير

**التاريخ:** 2026-08-07
**الحالة:** معتمد للتخطيط (بانتظار writing-plans)
**النطاق:** (1) أول حساب يُنشأ بالنظام يصير دوره `admin` تلقائياً بدل `cashier`، بما فيها ترقية تلقائية للحساب الوحيد الموجود حالياً بقاعدة البيانات الحية. (2) إخفاء حقل "سعر التكلفة" ومؤشر "الربح المتوقع" عن أي مستخدم دوره `cashier` بشاشات إضافة/تعديل المنتج. **لا يشمل** أي تعديل على قوانين RLS بقاعدة البيانات (تبقى كما هي، كما موثّق أدناه بقسم "خارج النطاق")، ولا واجهة تبديل دور يدوية، ولا صلاحيات دقيقة إضافية غير admin/cashier الثنائية الموجودة أصلاً.

## المشكلة

ميزة "إدارة الكاشير" ([[2026-08-07-cashier-management-design]]) مبنية وتعمل، لكن اكتُشف أثناء التحقق منها عيبان:

1. **لا توجد طريقة يصير فيها أي حساب `admin` تلقائياً.** الـ trigger الحالي (`handle_new_user`) يعطي كل حساب جديد دور `cashier` افتراضياً دائماً — بما فيها أول حساب (المالك نفسه). هذا يعني أي عميل جديد يستخدم هذا النظام (تركيب جديد) يعلق بنفس المشكلة: زر "الموظفون" ما يظهر لأحد، وما فيه واجهة أصلاً لترقية أول حساب — لازم تدخّل يدوي مباشر بقاعدة البيانات (SQL Editor بلوحة Supabase) كل مرة.
2. **بيانات الربح مكشوفة لأي مستخدم بشاشة المخزون بغض النظر عن دوره.** `ProductForm.tsx` و `QuickAddProductForm.tsx` (إضافة/تعديل منتج) يعرضون حقل "سعر التكلفة" ومكوّن `ProfitPreview` (يحسب الربح لكل قطعة ونسبة هامش الربح) لأي مستخدم يفتح النموذج، بدون أي تحقق من الدور. بما إن `/inventory` متاحة لأي حساب (مو `admin` بس)، فأي كاشير يقدر يفتح فورم إضافة منتج ويشوف تكلفة وربح كل منتج بالمحل — بالضبط الشي اللي المالك ما يريد الكاشير يشوفه.

## الهدف

1. أي حساب يُنشأ وقت ما يكون جدول `profiles` فاضي بالكامل → دوره `admin` تلقائياً.
2. الحساب الوحيد الموجود حالياً بقاعدة البيانات الحية (المسجّل اليوم كـ `cashier`) يترقّى لـ `admin` تلقائياً بمجرد تطبيق التغيير — بدون أي أمر SQL يدوي يشغّله المالك أو الوكيل.
3. حقل "سعر التكلفة" ومكوّن `ProfitPreview` يختفيان بالكامل من `ProductForm` و `QuickAddProductForm` لأي مستخدم دوره غير `admin`.

## القيود والقرارات المتفق عليها

- **التحقق من "هل الجدول فاضي" يصير داخل قاعدة البيانات نفسها (Postgres trigger)، مو بكود التطبيق** — لتفادي أي احتمال (نظري) لتعارض توقيت (race condition) لو صار إنشاء حسابين بنفس اللحظة عبر مسارين مختلفين (تطبيق + لوحة Supabase مباشرة). كود التطبيق (API route الموجود بميزة الموظفين) لا يتدخل بهذا القرار إطلاقاً.
- **الترقية التلقائية للحساب الحالي تُطبّق مرة وحدة وبأمان (idempotent):** ترقّي فقط أقدم حساب موجود (`created_at` الأصغر)، وفقط لو ماكو أي حساب `admin` موجود أصلاً بالجدول. إعادة تطبيق نفس التغيير مرة ثانية (لو صار بالخطأ) ما تأثر على شي.
- **إخفاء بيانات الربح بهذا التصميم = إخفاء بالواجهة فقط (client-side)، مو منع فعلي بقاعدة البيانات (RLS).** نفس النمط المستخدم أصلاً بشاشة "المبيعات" (`/sales`) اليوم — تحقق من `role === "admin"` بمكوّن الواجهة، وليس قانون RLS منفصل. هذا يعني: مستخدم كاشير متمرّس تقنياً ويعرف يستخدم أدوات المطوّر بالمتصفح يقدر نظرياً يشوف قيمة `cost_price` عبر طلبات الشبكة مباشرة. هذا قيد موجود أصلاً بكل الميزات المالية بالمشروع اليوم (موثّق كملاحظة "تشديد لاحق" بملف `00000000000000_init.sql`) وليس تراجع جديد بهذا التصميم — تشديد RLS الفعلي مؤجّل لتصميم منفصل لاحقاً (راجع "خارج النطاق").

## الطريقة التقنية

### الجزء 1: migration جديدة — `supabase/migrations/00000000000007_auto_admin_first_user.sql`

```sql
-- إعادة تعريف الدالة اللي تنشئ صف profiles تلقائياً عند أي تسجيل حساب جديد
create or replace function public.handle_new_user()
returns trigger as $$
declare
  assigned_role text;
begin
  if not exists (select 1 from public.profiles) then
    assigned_role := 'admin';
  else
    assigned_role := 'cashier';
  end if;

  insert into public.profiles (id, full_name, role)
  values (new.id, coalesce(new.raw_user_meta_data ->> 'full_name', new.email), assigned_role);
  return new;
end;
$$ language plpgsql security definer set search_path = public;

-- ترقية تلقائية لمرة وحدة: لو ماكو admin موجود أصلاً، رقّي أقدم حساب موجود
update public.profiles
set role = 'admin'
where id = (select id from public.profiles order by created_at asc limit 1)
  and not exists (select 1 from public.profiles where role = 'admin');
```

لا حاجة لأي migration منفصلة للـ backfill — نفس الملف يسوي الاثنين معاً (تعديل الدالة + تصحيح الحساب الحالي).

### الجزء 2: إخفاء حقل التكلفة والربح — `ProductForm.tsx` و `QuickAddProductForm.tsx`

- كلا المكوّنين يقرأ `role` عبر `useAuth()` من `context/AuthContext.tsx` (نفس المصدر المستخدم أصلاً بـ `Sidebar.tsx` و `/sales/page.tsx`).
- لو `role !== "admin"`: حقل "سعر التكلفة" (input) ومكوّن `<ProfitPreview />` لا يُعرضان إطلاقاً بالـ JSX (مو بس تعطيل/إخفاء بصري — إزالة كاملة من الشجرة).
- عند submit من قبل كاشير: `cost_price` تُرسل كـ `0` (نفس القيمة الافتراضية الحالية لمنتج جديد بدون تكلفة معروفة — المالك يقدر يعدّلها لاحقاً بنفسه من حسابه). لا حاجة لتغيير بـ `services/products.service.ts` — المنطق الحالي يقبل `cost_price: 0` بدون أي مشكلة.
- تعديل منتج موجود من قبل كاشير: نفس المبدأ — الحقل غير ظاهر، والقيمة المُرسلة تبقى القيمة الأصلية للمنتج (`product?.cost_price`) بدون تغيير، مو صفر (لتفادي كاشير "يصفّر" تكلفة منتج موجود بالغلط لمجرد إنه عدّل حقل ثاني بنفس الفورم).

## معالجة الأخطاء

- **تشغيل الـ migration أكثر من مرة:** آمن تماماً — `create or replace function` طبيعته استبدال، والـ `update` محمي بشرط `not exists (... role = 'admin')` فما يأثر شي بالمرة الثانية.
- **لو صار (نظرياً) أكثر من حساب موجود مسبقاً وكلهم `cashier`:** الترقية تصيب أقدم حساب فقط (الأكثر منطقية كونه "الحساب الأصلي")، مو كل الحسابات.
- **كاشير يعدّل منتج له `cost_price` من قبل (مو صفر) وما يشوف الحقل:** القيمة الأصلية تُحفظ كما هي عند الإرسال (راجع الجزء 2 أعلاه) — ما تنصفّر بالغلط.

## الاختبار

- منطق الـ trigger (SQL بحت) لا يُختبر بـ Vitest — يُتحقق منه يدوياً: تطبيق الـ migration، ثم تحديث الصفحة والتأكد من ظهور زر "الموظفون".
- تعديل `ProductForm`/`QuickAddProductForm`: فحص يدوي بحسابين مختلفين (admin وcashier تجريبي) — التأكد من اختفاء حقل التكلفة والربح تماماً لحساب الكاشير، وبقائه ظاهر لحساب المالك.
- `npm run typecheck && npm run lint && npm test && npm run build` لازم كلهم ناجحين قبل أي commit.

## خطوة يدوية مطلوبة (خارج نطاق الكود)

بعد commit ودفع (push) الـ migration، لازم تُطبّق فعلياً على قاعدة البيانات الحية عبر `supabase db push` (يحتاج تأكيد صريح من المالك قبل التنفيذ، كإجراء قياسي لأي عملية تمس قاعدة بيانات حية).

## خارج النطاق (مؤجَّل)

- تشديد قوانين RLS الفعلية بحيث كاشير يستحيل عليه يشوف `cost_price` حتى عبر طلبات شبكة مباشرة (يحتاج views منفصلة أو RPC بدل الاستعلام المباشر على الجداول — تصميم منفصل لاحقاً لو احتاج المالك مستوى حماية أعلى من الإخفاء بالواجهة).
- صلاحيات دقيقة أكثر من admin/cashier الثنائي (مثال: كاشير يقدر يعدّل مخزون بس مو يضيف منتج جديد).
- واجهة ترقية حساب من `cashier` إلى `admin` من داخل التطبيق (تبقى تحتاج تدخل يدوي بقاعدة البيانات، نفس القيد الموجود بتصميم إدارة الكاشير الأصلي).
