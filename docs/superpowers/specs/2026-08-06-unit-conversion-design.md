# تصميم: نظام تحويل الوحدات المتعدد (كارتون → كيس → قطعة)

**التاريخ:** 2026-08-06
**الحالة:** معتمد للتخطيط (بانتظار writing-plans)
**النطاق:** النظام الفرعي A فقط من خطة توسّع dddmart إلى Enterprise (راجع القسم "خارج النطاق" بالأسفل لبقية الأنظمة الفرعية B/C/D/E)

## المشكلة

حالياً `products.quantity` (عدد صحيح) و`products.unit` (نص حر) يمثلان وحدة بيع واحدة فقط لكل منتج. التاجر يشتري بالجملة (كارتون/كيس) ويبيع بالتجزئة (قطعة)، وما فيه طريقة يربط بين الوحدتين أو يبيع بأي وحدة غير القطعة مباشرة من الكاشير.

## الهدف

السماح لكل منتج، اختيارياً، بتعريف وحدات بيع إضافية أكبر من وحدة الأساس (مثلاً: قطعة ← كيس (×6) ← كارتون (×72))، كل وحدة بباركود وسعر بيع مستقلين، مع بقاء الرصيد مُتتبَّع دائماً برقم واحد بوحدة الأساس.

## القيود والقرارات المتفق عليها

- الهرمية **اختيارية** لكل منتج ومرنة بعدد المستويات (منتج بسيط بدون وحدات إضافية يبقى يشتغل زي ما هو).
- كل وحدة إضافية لها **باركود مستقل** يمسحه الكاشير مباشرة، و**سعر بيع مستقل يدوي** (مو محسوب تلقائياً من سعر القطعة × المعامل — قد يكون فيه خصم جملة).
- الرصيد المخزّن **دائماً رقم واحد بوحدة الأساس** (`products.quantity` يبقى كما هو تماماً، بدون تفكيك فعلي لكراتين/أكياس).
- أسماء الوحدات **نص حر لكل منتج** (زي `products.unit` الحالي)، مو من قائمة موحدة.
- التصميم **إضافي بالكامل (additive)** — صفر تعديل على أعمدة `products` الحالية، وصفر تعديل على منطق/توقيع RPC الخصم الحالي `adjust_product_stock(p_product_id uuid, p_delta integer)`.

## هيكل قاعدة البيانات

```sql
CREATE TABLE product_units (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  product_id uuid NOT NULL REFERENCES products(id) ON DELETE CASCADE,
  unit_name text NOT NULL,
  conversion_factor integer NOT NULL CHECK (conversion_factor > 1),
  barcode text NOT NULL UNIQUE,
  sale_price numeric(12,2) NOT NULL CHECK (sale_price >= 0),
  sort_order integer NOT NULL DEFAULT 0,
  is_active boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (product_id, unit_name)
);

ALTER TABLE sale_items
  ADD COLUMN unit_label text NULL,
  ADD COLUMN unit_conversion_factor integer NOT NULL DEFAULT 1;
```

نقاط التصميم:
- الوحدة الأساسية (القطعة) **لا تتكرر** كصف بـ`product_units` — يمثلها صف `products` نفسه دائماً.
- `conversion_factor` **صحيح (integer)** عمداً — يبقى متوافقاً 100% مع توقيع `adjust_product_stock` الحالي بدون أي تعديل عليه. `CHECK (conversion_factor > 1)` يمنع تعريف وحدة "أكبر" تساوي أو أصغر من القطعة.
- باركود كل وحدة UNIQUE داخل `product_units`، **وأيضاً** لازم يكون فريد مقابل `products.barcode` عبر الجدولين. بما إن Postgres ما يدعم UNIQUE عابر للجداول مباشرة، **trigger** على `products` و`product_units` (قبل INSERT/UPDATE) يتحقق من عدم وجود الباركود بالجدول الآخر ويرفض بخطأ واضح لو تصادم.
- `ON DELETE CASCADE`: حذف منتج يحذف وحداته تلقائياً — متوافق مع سلوك الحذف الحالي.
- `sort_order` يتحكم فقط بترتيب عرض الوحدات بواجهة إدارة المنتج وقائمة اختيار الوحدة بالكاشير (مثلاً قطعة ← كيس ← كارتون) — لا علاقة له بأي حساب.
- عمودا `sale_items` الجديدين **لقطة تاريخية مستقلة (snapshot)، مو FK** — تعديل/حذف تعريف وحدة لاحقاً لا يغيّر أو يكسر فواتير قديمة. `unit_label = NULL` يعني بيع بوحدة الأساس (الافتراضي، متوافق تماماً مع كل السجلات الحالية).

## تدفق البيانات بالكاشير (POS)

**1) بحث الباركود** — دالة جديدة `resolveBarcode(barcode)` تلف المنطق الحالي:
```
1. جرب products.barcode = X AND is_active=true   ← نفس استعلام getProductByBarcode الحالي، بدون تغيير
   → لو لقى: { kind: 'base', product }
2. إذا ما لقى، جرب product_units.barcode = X AND is_active=true (JOIN products WHERE is_active=true)
   → لو لقى: { kind: 'unit', product, unit }
3. ما لقى بالاثنين → null (نفس رسالة "باركود غير موجود" الحالية)
```
مسار "الأساس" (أغلب المنتجات الحالية) يمر بنفس سطر SQL الموجود اليوم بالضبط — صفر تغيير أداء أو سلوك للمنتجات بدون وحدات إضافية.

**2) خصم المخزون** — بدون أي تعديل على RPC `adjust_product_stock`. الفرق الوحيد: الـ`delta` المُرسل يصير `-(الكمية × conversion_factor)` بدل `-(الكمية)` لما البيع يكون بوحدة غير الأساس. مثال: مسح باركود كرتون (factor=24)، كمية 2 → `delta = -48`.

**3) توسيع `CartItem`** (`types/pos.ts`) بحقلين اختياريين فقط:
```typescript
interface CartItem {
  // ...الحقول الحالية بدون أي تغيير
  unitName?: string;             // "كارتون" — غير موجود = وحدة أساس
  unitConversionFactor?: number; // 24 — غير موجود = يُعامل كـ 1
}
```
`usePOS` (scanBarcode / updateQuantity / removeItem / clear) يستخدم `unitConversionFactor ?? 1` بكل حساب دلتا. أي كود حالي يتعامل مع `CartItem` بدون هالحقلين يستمر يشتغل بالضبط متل هسة.

**4) عرض الوحدة بالكاشير/الفاتورة** — حالياً `products.unit` ما يظهر إطلاقاً بـ`CartGrid.tsx` ولا `ReceiptPrinter.tsx`. لازم إضافة عرض بسيط (مثلاً "٢ × كارتون") بالمكونين — جزء ضروري من الميزة نفسها (بدون هذا الكاشير ما يميّز سطر كرتون عن سطر قطعة لنفس المنتج)، مو إضافة جانبية اختيارية.

**5) `createSale` بـ`services/sales.service.ts`** يكتب `unit_label`/`unit_conversion_factor` من `CartItem.unitName`/`unitConversionFactor` (بقيم افتراضية `null`/`1`) بالإضافة للأعمدة الحالية بدون تغيير.

## معالجة الأخطاء

| الحالة | السلوك |
|---|---|
| باركود وحدة يتصادم مع باركود موجود (منتج أو وحدة ثانية) | الـtrigger يرفض العملية بـPostgres exception → رسالة عربية واضحة بشاشة إدارة المنتج |
| `conversion_factor` ≤ 1 عند الإدخال | CHECK بقاعدة البيانات يرفض + تحقق بالواجهة قبل الإرسال |
| مخزون غير كافٍ (كرتون كامل ما يوفي) | نفس حارس RPC الحالي (يرجع نتيجة فاضية/null) — رسالة الخطأ تتحسّن لتوضّح "متوفر X كرتون فقط" بدل رقم قطع مربك |
| حذف/تعطيل وحدة مستخدمة بفواتير سابقة | لا تأثير — `sale_items` لقطة مستقلة غير مرتبطة بـFK |

## خطة الاختبارات

**مستوى قاعدة البيانات:**
- CHECK يرفض `conversion_factor` = 0، 1، -5
- UNIQUE يرفض تكرار `unit_name` لنفس `product_id`
- الـtrigger يرفض باركود متصادم بالاتجاهين (وحدة↔منتج، ومنتج↔وحدة)
- `ON DELETE CASCADE` يحذف صفوف `product_units` عند حذف المنتج الأب

**مستوى الخدمات:**
- `resolveBarcode` يرجع النوع الصحيح (`base` / `unit` / `null`) لكل حالة اختبار
- حساب الـdelta المرسل لـ`adjust_product_stock` يستخدم `conversion_factor` بشكل صحيح
- **اختبار ارتداد (regression) إلزامي:** بيع منتج بدون وحدات إضافية يكتب بالضبط نفس أعمدة `sale_items` الحالية (`unit_label = null`, `unit_conversion_factor = 1`) — يضمن عدم كسر أي فاتورة أو تقرير حالي

**يدوي بعد التنفيذ:**
- مسح باركود كرتون فعلي بالـPOS، تأكيد نقصان `products.quantity` بالمقدار الصحيح
- سلامة كل الميزات الحالية (الأرشيف، تقارير المبيعات، البحث اليدوي، شاشة المخزون) بدون كسر

## خارج النطاق (أنظمة فرعية منفصلة، كل وحدة بـspec مستقل لاحقاً)

- **B — الدفعات وتواريخ الصلاحية / FIFO:** يعتمد معمارياً على هذا التصميم (الدفعة تحتاج تعرف وحدة الأساس)، يُصمَّم بجولة brainstorming منفصلة بعد تنفيذ A.
- **C — دفتر ديون العملاء وحسابات الموردين (آجل).**
- **D — تسليم الشفتات وعجز الكاشير (Z-Report / Blind Closing).**
- **E — تفكيك باركود الميزان الإلكتروني** — مرتبط منطقياً بمفهوم "الوحدة" هنا (الوزن كوحدة)، لكن يُصمَّم كـspec مستقل.

## ملاحظة تنفيذية

خطة التنفيذ (بعد اعتماد هذا الـspec عبر writing-plans) ستستخدم نمط "عميل يخطط ثم عميل ينفذ" (Plan agent → execute agent) المعتاد بهذا المشروع، مع Reviewer Agent يكتب اختبارات الـSchema/العقود قبل أي كود تنفيذي (TDD)، والتحقق من عدم كسر أي من: الأرشيف، تقارير المبيعات، شاشة المخزون، مسار الكاشير الحالي.
