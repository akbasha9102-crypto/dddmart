# تصميم: إدارة الكاشير (إضافة/تفعيل/تعطيل موظفين من داخل التطبيق)

**التاريخ:** 2026-08-07
**الحالة:** معتمد للتخطيط (بانتظار writing-plans)
**النطاق:** يسمح لمستخدم `admin` بإنشاء حساب دخول جديد بدور `cashier` من داخل التطبيق، وعرض قائمة الموظفين، وتفعيل/تعطيل حسابهم (تعطيل حقيقي يمنع تسجيل الدخول فعلياً، مو مجرد علامة بقاعدة البيانات). **لا يشمل** صلاحيات دقيقة إضافية غير admin/cashier، ولا نظام دعوة بالإيميل، ولا شاشة تغيير كلمة مرور ذاتية للموظف، ولا ترقية حساب لـ admin من داخل التطبيق.

## المشكلة

حالياً كل المستخدمين يدخلون بحساب واحد مشترك. لا توجد طريقة من داخل التطبيق لصاحب المحل (admin) يعطي كل كاشير حساب دخول خاص فيه، ولا لمراقبة/تعطيل حساب موظف ترك الشغل. إنشاء حسابات جديدة يتطلب حالياً الدخول للوحة تحكم Supabase مباشرة (خارج التطبيق بالكامل)، وحتى لو عندك حساب معطّل بجدول `profiles.is_active`، **هذا العمود غير مُتحقق منه بأي مكان بالكود اليوم** — أي حساب يقدر يسجّل دخول بغض النظر عن قيمة هذا العمود.

## الهدف

1. شاشة "الموظفون" (`/employees`, `admin` فقط) تعرض كل الموظفين (الاسم، الدور، حالة التفعيل).
2. زر "إضافة كاشير" ينشئ حساب دخول فعلي (إيميل + كلمة مرور يختارها المالك) بدور `cashier` تلقائياً.
3. زر تفعيل/تعطيل بجانب كل موظف — التعطيل **يمنع تسجيل الدخول فعلياً عند Supabase نفسها**، مو بس علامة بالواجهة.

## القيود والقرارات المتفق عليها

- **صلاحيات ثنائية فقط** (`admin`/`cashier`) — لا صلاحيات دقيقة إضافية بهذا التصميم.
- **المالك يختار كلمة المرور مباشرة** عند الإضافة ويسلّمها للموظف شخصياً — لا نظام دعوة/إيميل (لا توجد بنية بريد إلكتروني مُعدّة بالمشروع أصلاً).
- **لا شاشة تغيير كلمة مرور ذاتية للموظف** بهذا التصميم — لو الموظف حب يغيّرها لازم يطلب من المالك يعمل حساب جديد أو (لاحقاً، خارج النطاق) نضيف هذي الميزة.
- **إنشاء حساب من هذي الشاشة ينتج دائماً `cashier`** — ما فيه طريقة من داخل التطبيق ترفّع حساب لـ `admin`؛ هذا يبقى إجراء يدوي من لوحة تحكم Supabase (نفس القيد الموجود على حساب المالك نفسه اليوم).
- **حماية من قفل الحساب الوحيد:** الـ API يرفض طلب تعطيل لو كان المستخدم يحاول يعطّل **حسابه هو نفسه** — لتفادي سيناريو "المالك يعطّل حسابه بالغلط ويصير ما يقدر يدخل للنظام خالص".
- **التحقق من الصلاحية يصير على السيرفر، مو بالواجهة فقط** — حتى لو حاول شخص غير admin يستدعي الـ API مباشرة (متجاوزاً الواجهة)، السيرفر يرفض الطلب.

## الطريقة التقنية

### لماذا نحتاج نقطة اتصال جديدة بالسيرفر (API Route)
إنشاء حساب دخول جديد أو منعه من الدخول هي عمليات على **نظام المصادقة** مال Supabase (`auth.users`)، مو عمليات عادية على جدول بيانات. المفتاح العام (anon key) اللي التطبيق يستخدمه اليوم بكل شاشاته **لا يملك صلاحية** يسوي هذي العمليات بغض النظر عن دور المستخدم، لأنه مقيّد بقوانين RLS المصمَّمة للبيانات فقط. هذا يتطلب **المفتاح الإداري (`service_role`)** من Supabase، اللي يتخطى كل القوانين وله صلاحية كاملة — بما فيها التحكم بالحسابات. هذا أول استخدام لهذا المفتاح بالمشروع، وأول API route بالكامل (`app/api/` فاضي حالياً).

### الملفات الجديدة
- **`lib/supabase/admin.ts`** (خادم فقط، لا يُستورد أبداً من أي ملف `"use client"`): ينشئ عميل Supabase بمفتاح `SUPABASE_SERVICE_ROLE_KEY` (متغيّر بيئة جديد، **بدون `NEXT_PUBLIC_` بادئة** — هذا يضمن Next.js ما يسرّبه للمتصفح إطلاقاً، بعكس بقية المفاتيح الحالية اللي كلها `NEXT_PUBLIC_*`).
- **`app/api/employees/route.ts`**:
  - `GET`: (اختياري — القائمة ممكن تُجلب مباشرة من العميل بما إن RLS الحالية على `profiles` تسمح بالفعل لأي مستخدم مسجل دخول يقرأ كل الصفوف؛ **القرار: لا حاجة لهذا الـ endpoint، الشاشة تجلب القائمة مباشرة عبر `lib/supabase/client.ts` العادي**).
  - `POST` (إضافة كاشير): يتحقق أولاً إن الجالب `admin` (يقرأ الجلسة عبر `lib/supabase/server.ts`، يجيب `profiles.role` لصاحب الجلسة)، ولو لا يرجّع `403`. لو `admin`: يستدعي `adminClient.auth.admin.createUser({ email, password, email_confirm: true, user_metadata: { full_name } })`. الـ trigger الموجود أصلاً بقاعدة البيانات (`handle_new_user`) يتكفّل تلقائياً بإنشاء صف `profiles` المرتبط بدور `cashier` افتراضياً — **لا حاجة لإدراج يدوي بجدول `profiles`**.
- **`app/api/employees/[id]/route.ts`**:
  - `PATCH` (تفعيل/تعطيل): نفس التحقق من `admin`. يرفض لو `id === مستخدم الجلسة نفسه` (حماية القفل الذاتي). لو المطلوب تعطيل: يستدعي `adminClient.auth.admin.updateUserById(id, { ban_duration: "876000h" })` (فعلياً دائم) **ثم** `adminClient.from("profiles").update({ is_active: false }).eq("id", id)` (تحديث مباشر عبر عميل الخدمة، متجاوزاً قيد RLS الحالي "self update profile" اللي يمنع تعديل صف مستخدم آخر). التفعيل يعكس نفس الخطوتين (`ban_duration: "none"`, `is_active: true`).

### شاشة "الموظفون" (`app/(dashboard)/employees/page.tsx`)
- مقيّدة بنفس نمط `role === "admin"` المبني أصلاً بميزة الأرباح (`useAuth()` من `context/AuthContext.tsx`) — تُخفى/تُمنع عن `cashier` بنفس الأسلوب بالضبط (تحديداً كل نقاط الحماية الثلاث: `/sales/page.tsx` والتحقق من رابط `Navbar`/`Sidebar`/`BottomNav` عبر `visibleNavLinks(role)` الموجودة أصلاً — الإضافة الجديدة هنا هي بس إضافة `/employees` لنفس دالة الفلترة تلك).
- قائمة الموظفين: تُجلب مباشرة من `profiles` (RLS الحالية تسمح، بدون أي API). عرض: `full_name`، `role` (شارة "المالك" لو admin، "كاشير" لو cashier)، دائرة فعّال/معطّل.
- زر "+ إضافة كاشير": نموذج بسيط (اسم كامل، إيميل، كلمة مرور مؤقتة) → `POST /api/employees` → عند النجاح: تحديث القائمة + رسالة "تم إنشاء الحساب، أعطي هذه البيانات للكاشير".
- ضغط دائرة الحالة → `PATCH /api/employees/[id]` → تحديث فوري بالواجهة عند النجاح.

## معالجة الأخطاء

- **مستخدم غير admin يستدعي الـ API مباشرة** (متجاوزاً الواجهة): `403` برسالة عربية، بدون أي تسريب بيانات.
- **إيميل مستخدم من قبل:** Supabase يرجّع خطأ "already registered" → رسالة عربية "هذا الإيميل مستخدم من قبل".
- **كلمة مرور قصيرة جداً** (أقل من الحد الأدنى لـ Supabase، 6 أحرف افتراضياً): رسالة عربية توضح الحد الأدنى.
- **محاولة تعطيل الحساب الذاتي:** `400` برسالة "ما تقدر تعطّل حسابك أنت نفسك".
- **`SUPABASE_SERVICE_ROLE_KEY` غير موجود بمتغيرات البيئة:** الـ API يفشل بخطأ واضح بالسجلات (لا يعرض المفتاح نفسه)؛ هذا سيناريو تشغيلي (بيئة لسا ما اتظبطت) مو خطأ برمجي — يحتاج المالك يضيف المتغيّر (راجع "خطوة يدوية مطلوبة" بالأسفل).

## خطوة يدوية مطلوبة (خارج نطاق الكود)

قبل ما هذي الميزة تشتغل فعلياً، لازم المالك:
1. يجيب `service_role key` من لوحة تحكم Supabase (Project Settings → API).
2. يضيفه كمتغيّر بيئة باسم `SUPABASE_SERVICE_ROLE_KEY` — محلياً بملف `.env.local` (مو داخل المحادثة)، وبمشروع Vercel (Environment Variables) للنسخة المنشورة على الإنترنت.

هذي الخطوة **لا يقدر أي عميل من الثلاثة (مراجع/منفّذ/مدقّق) يسويها بدلاً عنك** — المفتاح حساس ولازم يوصل من عندك مباشرة.

## الاختبار

- اختبار وحدة للدالة اللي تتحقق "هل هذا المستخدم admin؟" (منطق نقي، منفصل عن استدعاء Supabase الفعلي) — يغطي: admin حقيقي (يسمح)، cashier (يرفض)، role غير معروف/null (يرفض).
- اختبار وحدة لمنطق "منع تعطيل الحساب الذاتي" (مقارنة `id` الهدف مع `id` الجالسة).
- استدعاءات `auth.admin.*` نفسها **صعبة الاختبار بنمط "fake" الموجود بالمشروع حالياً** (لا يوجد fake لهذا الجزء من Supabase SDK بعد) — يُكتفى باختبار المنطق النقي أعلاه، والتحقق اليدوي الفعلي (تشغيل السيرفر محلياً، إضافة كاشير تجريبي، تسجيل دخول فيه، تعطيله، التأكد إنه يرفض الدخول) بدل اختبار آلي كامل لهذي المسارات تحديداً.
- `npm run typecheck && npm run lint && npm test && npm run build` لازم كلهم ناجحين قبل أي commit.

## خارج النطاق (مؤجَّل)

- صلاحيات دقيقة أكثر من admin/cashier الثنائي.
- دعوة بالإيميل بدل كلمة مرور مباشرة (يحتاج إعداد بريد إلكتروني بمشروع Supabase أولاً).
- شاشة "تغيير كلمة المرور" ذاتية للموظف.
- ترقية حساب من `cashier` إلى `admin` من داخل التطبيق.
- حذف حساب نهائياً (بس تعطيل/تفعيل بهذا التصميم).
