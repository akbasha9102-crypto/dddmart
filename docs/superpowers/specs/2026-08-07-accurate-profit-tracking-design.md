# تصميم: دقة تتبع الأرباح + إخفاؤها عن الكاشير

**التاريخ:** 2026-08-07
**الحالة:** معتمد للتخطيط (بانتظار writing-plans)
**النطاق:** إصلاح دقة حساب الأرباح تاريخياً + تقييد الوصول لصفحة الأرباح حسب دور المستخدم (`admin`/`cashier`) المخزّن أصلاً بقاعدة البيانات. **لا يشمل** بناء واجهة "إضافة/إدارة كاشير" من داخل التطبيق — هذا مشروع منفصل لاحق (راجع "خارج النطاق").

## المشكلة

كل تقارير الأرباح الحالية (`getDailySalesSummary`, `getDailyReportDetails`, `getSalesTrend`, `getProductRanking`, `getCategoryRanking` في `services/sales.service.ts`) تحسب الربح بمقارنة `unit_price` المسجّل بالفاتورة مع **سعر التكلفة الحالي** لكل منتج (`products.cost_price` وقت تشغيل التقرير، مو وقت البيع الفعلي). لو تغيّر سعر شراء منتج بعد بيعه، كل التقارير القديمة اللي فيها هذا المنتج تتغيّر أرقامها رجوعاً بالزمن — تقرير أرباح أمس ممكن يعرض رقم مختلف لو فتحته اليوم بعد ما غيّرت سعر التكلفة.

بالإضافة، **أي مستخدم مسجّل دخول** (حتى لو دوره `cashier` بقاعدة البيانات) يقدر حالياً يوصل لصفحة `/sales` بكامل تفاصيل الأرباح — لأن التطبيق أصلاً ما يقرأ عمود `role` من `profiles` بأي مكان بالواجهة.

## الهدف

1. كل عملية بيع جديدة تسجّل سعر التكلفة الفعلي **لحظة إضافة المنتج للسلة**، بشكل دائم وغير قابل للتغيّر لاحقاً، فتصير كل تقارير الأرباح (من لحظة إطلاق هذا التعديل فصاعداً) دقيقة ٪100 ومستقرة عبر الزمن.
2. صفحة "تقارير المبيعات" (`/sales`) — اللي تعرض الأرباح والمبيعات والترتيب — تظهر فقط للمستخدم اللي دوره `admin`، وتُخفى/تُمنع عن `cashier`.

## القيود والقرارات المتفق عليها

- **البيانات القديمة لا تُعدَّل رجعياً** — المبيعات اللي صارت قبل هذا التعديل تبقى تقديرية زي ما هي اليوم (بدون backfill). فقط المبيعات الجديدة من لحظة التطبيق تصير دقيقة.
- **آلية اللقطة (snapshot) على مستوى الكود (Application-level)، مو Database Trigger** — تنسجم مع بنية المشروع الحالية (كل منطق الأعمال بطبقة `services/`، صفر triggers على جداول المبيعات حالياً).
- **لقطة السعر تُؤخذ وقت الإضافة للسلة (add-to-cart)، مو وقت الدفع النهائي (checkout)** — لأن هذي نفس اللحظة اللي `unit_price` (سعر البيع) يُلقط فيها اليوم بالضبط (`productToCartItem`/`productUnitToCartItem`)، ولأنها الوحيدة المتوافقة صح مع ميزة البيع أوفلاين: لو صار البيع بدون نت، لازم سعر التكلفة يعكس لحظة البيع الحقيقية، مو لحظة المزامنة لاحقاً.
- **تبسيط التقارير الأربعة المكرِّرة كأثر جانبي مقصود** — بعد توفر `sale_items.cost_price`، الأربعة أماكن اللي تكرر نفس منطق "اجلب سعر التكلفة الحالي من المنتجات ثم احسب" تُبسَّط لقراءة العمود مباشرة، فيزول التكرار البرمجي مو بس الخطأ.
- **تقييد الوصول لصفحة الأرباح بمستوى الواجهة فقط (UI-level)، مو بمستوى قاعدة البيانات (RLS)** — قرار واعٍ ومقصود بعد نقاش صريح مع المالك. **هذا يعني إن الحماية غير مطلقة**: قواعد RLS الحالية على جداول `sales`/`sale_items` مفتوحة لأي مستخدم مسجّل دخول (`using (true)`)، فمستخدم كاشير يفهم بالتقنية يقدر نظرياً يستعلم مباشرة عن البيانات ويتجاوز إخفاء الواجهة. حماية حقيقية على مستوى البيانات تحتاج View/دالة محمية بمشروع الصلاحيات الشامل المؤجَّل — موثّقة هنا كخطر معروف ومقبول للمرحلة الحالية.
- **الفصل الفعلي بين حساب المالك وحساب الكاشير يبقى إجراء يدوي خارج التطبيق** (من لوحة تحكم Supabase) لأن التطبيق حالياً حساب واحد مشترك للجميع، وما فيه صفحة "إضافة موظف" بعد. هذا التصميم يجهّز **الأساس البرمجي** (قراءة الدور + التقييد حسبه) اللي مشروع "إدارة الكاشير" القادم سيبني فوقه.

## هيكل قاعدة البيانات

```sql
-- migration: 00000000000006_snapshot_sale_item_cost_price.sql
ALTER TABLE sale_items
  ADD COLUMN cost_price numeric(12,2) NOT NULL DEFAULT 0;
```

نقاط التصميم:
- عمود **لقطة تاريخية مستقلة (snapshot)، مو FK** لجدول `products` — نفس نمط `unit_label`/`unit_conversion_factor` الموجودين أصلاً بنفس الجدول (راجع تصميم تحويل الوحدات). تعديل `products.cost_price` لاحقاً لا يغيّر أي فاتورة قديمة.
- `DEFAULT 0` يخلي كل صفوف `sale_items` القديمة تُقرأ بـ`cost_price = 0` (ربح = كامل سعر البيع) بدل NULL — الكود اللي يقرأ هذا العمود بالتقارير لازم يتعامل معه كـ"غير معروف تاريخياً" لا يُحتسب كخطأ (راجع "معالجة الأخطاء" بالأسفل).
- لا تعديل على أي RLS policy موجودة — العمود الجديد يورث نفس صلاحيات `sale_items` الحالية.

## تدفق البيانات

**1) عند إضافة منتج للسلة (`hooks/usePOS.ts#addProductToCart`):**
`decrementStock`/المسار الأوفلاين يرجّع بيانات المنتج المحدّثة (تتضمن `cost_price` أصلاً). `types/pos.ts#CartItem` يكتسب حقل جديد `costPrice: number`، يُملأ بـ:
- `productToCartItem`: `costPrice: product.cost_price` (وحدة الأساس).
- `productUnitToCartItem`: `costPrice: product.cost_price * unit.conversion_factor` (نفس منطق تحويل الكمية للوحدة الأكبر الموجود أصلاً لحساب `toBaseUnits`، مطبّق هنا على التكلفة).

**2) عند الدفع (`services/sales.service.ts#buildSaleItemRows`):**
دالة بناء صفوف `sale_items` (الدالة النقية الموجودة أصلاً، مفصولة عن `createSale` لتسهيل الاختبار) تضيف `cost_price: item.costPrice` لكل صف — بدون أي استعلام إضافي لقاعدة البيانات وقت الدفع (القيمة موجودة أصلاً بعنصر السلة من لحظة الإضافة).

**3) بالتقارير — الأربعة دوال بـ`services/sales.service.ts`:**
`computeProfitForSales` (يخدم `getDailySalesSummary` و`getDailyReportDetails`)، `getSalesTrend`، `getProductRanking`، `getCategoryRanking` — كل وحدة فيها اليوم تجلب `sale_items` ثم تستعلم بشكل منفصل عن `products` لجلب `cost_price` الحالي وتربطهم يدوياً. بعد التعديل: `select` على `sale_items` تضيف عمود `cost_price` مباشرة، ويُحذف استعلام `products` الإضافي بالكامل من الدوال الأربعة (تبسيط + تسريع، أقل استعلام واحد لكل تقرير).

**4) تقييد صفحة الأرباح:**
- `context/AuthContext.tsx` يكتسب حقل جديد `role: UserRole | null` بجانب `user` الموجود — يُجلب بجلب سجل `profiles` المطابق لـ`user.id` عند تسجيل الدخول (استعلام واحد إضافي، `select role from profiles where id = auth.uid()`، نفس نمط استعلام `useEffect` الموجود أصلاً بالملف لجلب `user`).
- الصفحة `app/(dashboard)/sales/page.tsx` تتحقق من `role === "admin"` وتعرض رسالة "هذي الصفحة للمالك فقط" (أو تُعيد التوجيه لـ`/pos`) لو الدور غير ذلك أو لسا يحمّل.
- رابط "تقارير المبيعات" بـ`components/shared/Sidebar.tsx`/`BottomNav.tsx` يُخفى بنفس الشرط.

## معالجة الأخطاء والحالات الحدّية

- **منتج محذوف قبل البيع لكن بعد إضافته للسلة (نادر):** لا يتغيّر — نفس السلوك الحالي لـ`unit_price` (اللقطة تُؤخذ وقت الإضافة، فحذف المنتج لاحقاً لا يؤثر على الفاتورة).
- **فاتورة قديمة (`cost_price = 0` من الـDEFAULT):** التقارير تحسبها بربح = سعر البيع كامل، وهذا **متوقع ومقصود** بما إنها بيانات تقديرية أصلاً من قبل هذا التعديل — لا حاجة لعلامة "غير معروف" منفصلة بالواجهة حالياً (خارج النطاق، ممكن يُضاف لاحقاً لو صار مطلوب).
- **`role` لسا يحمّل (null) عند فتح `/sales` مباشرة برابط:** تُعامَل نفس معاملة "غير مصرّح" مؤقتاً (لا تُعرض الصفحة) لحد ما يوصل الدور الفعلي، تفادياً لومضة عرض بيانات حساسة (flash of unauthorized content).

## الاختبار

- اختبار وحدة جديد لـ`buildSaleItemRows`: يتأكد إن `cost_price` يُنسخ صح من `CartItem.costPrice` لعنصر بوحدة أساس وعنصر بوحدة أكبر (كارتون).
- اختبار وحدة جديد لـ`productToCartItem`/`productUnitToCartItem`: يتأكد من حساب `costPrice` الصحيح (مباشر مقابل مضروب بمعامل التحويل).
- تحديث/تبسيط أي اختبار موجود بـ`sales.service.test.ts` يتأثر بحذف استعلام `products` من دوال التقارير.
- `services/products.service.test.ts` و`sales.service.test.ts` الحاليين يستمرون ناجحين بدون تعديل على سلوكهم الأساسي.
- `npm run typecheck && npm run lint && npm test && npm run build` — لازم كلهم ناجحين قبل أي commit.

## خارج النطاق (مؤجَّل لمشاريع لاحقة)

- **نظام صلاحيات شامل** (تعديل مخزون، حذف منتجات، إدارة كل الشاشات حسب الدور) — هذا التصميم يقيّد صفحة الأرباح فقط.
- **حماية على مستوى قاعدة البيانات (RLS/column-level)** لعمود التكلفة والأرباح — موثّق كخطر معروف أعلاه.
- **واجهة "إضافة/إدارة كاشير" من داخل التطبيق** (إنشاء حسابات جديدة، تعيين أدوار، تعطيل حساب) — مشروع منفصل قادم مباشرة بعد هذا، يحتاج كود سيرفر بصلاحية إدارية خاصة (Supabase service role) وتصميمه الخاص.
- **إعادة حساب/تصحيح رجعي (backfill)** لأرباح المبيعات القديمة.
